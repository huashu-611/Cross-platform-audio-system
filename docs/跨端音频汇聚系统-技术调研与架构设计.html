核心结论

没有任何一个现成开源项目能直接满足这个场景。不是"不太好用"，是三个必要条件同时成立的项目不存在： ① 抓取「别的 App」的系统播放音频、② 多路汇聚到一台设备并混音、③ 延迟低到能对齐画面。市面上每个项目最多满足两条。

01需求的形式化

把"想让声音从一台设备的喇叭出来"翻译成工程约束。

场景：N 台源设备各自播放不同内容，1 台 Hub（Windows PC 或 Android）的扬声器 / 有线耳机是唯一声音出口。源端可以是 Hub 自己。

编号需求技术翻译
R1源端要能抓「别人的 App」只有系统级采集 API 可行（Android AudioPlaybackCapture / Windows WASAPI loopback / macOS Core Audio Tap）。应用内播放器抓自己的音频不算解法
R2单向、低延迟、允许丢包UDP。丢一个 10 ms 帧用 PLC 补，比等 200 ms 重传好得多
R3Hub 侧 N 路同时混音每源独立解码 + 抖动缓冲 + 求和；还要能跟 Hub 本机音频共存
R4每路延迟「低且稳定」听者同时看着源设备的屏幕，所以是音画同步问题，不是"能听见就行"
R5长时间运行不漂移源与 Hub 的晶振不同源，必须做异步采样率转换（ASRC）

三个最容易被忽略、但决定项目成败的约束

约束一 · 出口设备是天花板

Hub 如果接蓝牙耳机，链路一次性 +150~250 ms（A2DP 缓冲 + 编解码），你的 60 ms 优化瞬间归零。 产品上必须主动检测输出设备类型并警告，这比任何算法优化都重要。USB-C / 3.5 mm 有线耳机、USB DAC 才有意义。

约束二 · 源端采集是硬上限

Android 的 AudioPlaybackCapture 抓不到：DRM 内容（Netflix / 部分音乐平台）、在 Manifest 里声明 allowAudioPlaybackCapture=false 的 App、以及非 USAGE_MEDIA/GAME/UNKNOWN 的音频。 这不是 bug，是设计。产品文案不能承诺"什么都能抓"。

约束三 · 多源之间没有共同时间轴

Snapcast 的同步前提是"所有客户端播同一份内容"，所以可以对同一个采样序号对齐。 我们这里 A 在放 B 站、B 在放游戏、C 在放音乐 —— 没有共同的内容时间轴。 需要的是"每路的延迟锁定到同一个目标值 L"，这是完全不同的问题（详见 §07）。

2.3 为什么每一个都不能直接用

① Snapcast 类：拓扑反了

Snapcast 的同步算法值得抄 —— 服务端给每个 PCM 块打单调时钟时间戳 t_s，客户端每次连发 timesync 消息估计 offset d（取最近 50 次的中位数抗抖动）， 收到块后在 t_s + d + bufferMs − latency 时刻播出。这套设计在 1→N 场景里是最优解。

但它没有"多源混音"这一层。snapserver 可以配置多路 [stream]，但每个客户端只能订阅一路；服务端不做求和。 要拿它改造成你的场景，等于重写服务端的音频图 —— 工作量不比自研小，还背上了一个为 1 秒缓冲设计的 TCP 传输层。

② PulseAudio / PipeWire / VBAN 类：拓扑对了，平台不对

PulseAudio 的 module-native-protocol-tcp 其实是最接近你需求的东西：任意客户端 PULSE_SERVER=tcp:host，音频直接灌进服务端的 sink， 服务端自动多源混音，latency_msec 从 16.0 起可配（旧版 tunnel 模块固定 250 ms）。实测 20–120 ms 可达。

问题只有一个但致命：它是 Linux 的。你的宿端是 Windows 和 Android，而 PulseAudio 的 Windows 移植早已荒废、Android 上不存在。 另外老 module-tunnel-sink 有个著名的坑：改延迟的代码是注释掉的，tunnel-sink-new 的动态延迟只会落在 11 / 75 / 200 ms 三档（取决于哪个 App 触发 sink 从 idle 转 active）。

VBAN + Voicemeeter 是 Windows 上唯一开箱即用的多源汇聚：UDP 传未压缩 PCM（1–8 声道、任意采样率），Voicemeeter 收多路 VBAN 混音后输出到任一硬件口，有线 LAN 下 10–30 ms。 代价是 Voicemeeter 闭源、UI 极其难用、且 Android 端没有官方 VBAN 发送器（得自己按协议写，好在协议是公开的、结构简单）。 它非常适合做 P0 阶段的对照组：先证明"Windows 宿端 + 多源混音"体验成立，再决定要不要自研。

③ SonoBus / Jamulus 类：混音模型对了，采集方式错了

SonoBus 是全平台（Win / mac / Linux / iOS / Android）、GPL、JUCE + Opus、每个 peer 混所有入流、手动可调抖动缓冲 —— 从"传输 + 混音"角度看几乎是现成的。

但它采集的是输入设备（麦克风 / 声卡 line-in），不是系统播放音频。Windows 上还能靠 VB-Cable 把系统声音绕成"输入"，Android 上完全做不到 —— 没有虚拟声卡的公共 API。 所以它只能当参考实现读代码，不能当产品底座。

④ sndcpy 方向对、延迟不对

sndcpy 是 scrcpy 作者的音频版：Android AudioPlaybackCapture → 原始 PCM → adb 隧道 → PC 上 VLC 播。方向完全正确，采集部分可以直接借鉴。

但它的延迟 150–300 ms，瓶颈是 VLC 的 --network-caching（默认 1000 ms，手动压到 100 ms）加上 adb over TCP 的缓冲。 它证明了"采集可行"，也证明了"采集不是瓶颈" —— 这正是自研时该换掉的部分。

5.1 采集端的关键实现点

Android 侧（决定项目上限的一块）：

  • 用 AudioRecord 而不是 MediaRecorder；AudioPlaybackCaptureConfiguration 里用 addMatchingUsage() 而不是 excludeUsage()（两者不能混用）
  • 缓冲设成 2× burst，PERFORMANCE_MODE_LOW_LATENCY；采集回调跑在独立高优先级线程，绝不分配内存
  • 必须起前台服务（foregroundServiceType="mediaProjection"）+ WifiLock(WIFI_MODE_FULL_HIGH_PERF)，否则 3 分钟后 Doze 就把网络限流，延迟从 60 ms 跳到 500 ms
  • Android 14+ 的 MediaProjection 授权是每次会话一次，不能持久化；UI 上要做好"重新授权"的引导

Windows 侧：如果 Hub 同时要抓本机音频（Hub 自己也是源），必须用 PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE 排除自己， 否则 Hub 播放出来的远程音频会被自己再抓一遍 → 无限反馈。这是最容易踩且最难查的坑。

统一内部格式

48 kHz / float32 / stereo。单声道源上混为双声道；44.1 kHz 源在采集侧重采样一次，避免链路中途多次转换。 不要在 Hub 侧做采样率转换（除了时钟环需要的极小比率调整），多级重采样会累积相位误差和延迟。

6.1 为什么是 UDP，不是 TCP

TCP 的丢包重传会造成队头阻塞：一个包丢了，后面所有包都要等它重传到达才能交付。WiFi 下一次重传就是 1–2 个 RTT，30–80 ms， 而且这 30–80 ms 会永久累积进缓冲 —— 因为 TCP 不丢数据，你只能把缓冲越撑越大。对"延迟必须稳定在 60 ms"是灾难。

Snapcast 用 TCP 是对的，因为它的默认缓冲是 1000 ms，听音乐场景下 1000 ms 对 1030 ms 没有区别。我们不行。

6.2 为什么也不是 WebRTC

环节WebRTC 的典型值对我们的影响
抖动缓冲（NetEq）40–200 ms，自适应我们只要 20–40 ms。jitterBufferTarget 只能设下界，实际值仍由 NetEq 决定
ICE / DTLS 握手100–500 ms（一次性）可接受，但增加了工程复杂度
Opus 默认 ptime20 ms可改，但 WebRTC 生态默认按 20 ms 优化
回声消除 / AGC默认全开必须全关。AEC 和 AGC 会破坏音乐信号，也会加 10–20 ms 处理延迟
浏览器采集getDisplayMedia 只能抓标签页无法抓整个系统音频

但 WebRTC 有一个思想要抄：NetEq 的 Accelerate / Preemptive Expand —— 缓冲过高时通过"去掉一个基音周期"加速播放， 过低时"插入一个基音周期"减速，改变时序但不改变音高。这正是我们外环要做的事，比丢帧/补零优雅得多。

07时钟同步

这是整套系统里最容易做错的一节，因为大多数人对"同步"的理解是错的。

7.1 先澄清：我们需要的到底是哪种"同步"

同步语义定义本场景
采样级同步多设备播同一份内容，同一采样在同一物理时刻出声（Snapcast / AirPlay 干的事）不需要 各源内容不同，没有共同时间轴
延迟一致多源的端到端延迟差 < 阈值（建议 < 10 ms）需要 否则切换源时"时快时慢"，很怪
音画对齐单源的音频延迟稳定且低于感知阈值最重要 见 §09
时钟域同步源与 Hub 的采样率节奏一致，长时间不漂移需要 否则 1 小时必崩
一句话记住

我们做的不是"让多台设备同时出声"，而是"让每一路的延迟都锁死在同一个目标值上，并且这个值不随时间和网络波动"。 前者是 Snapcast 的同步问题，后者是控制系统的锁定问题。

7.2 双环结构

把"抗抖动"和"消漂移"拆成两个时间尺度完全不同的环。混在一起做是最常见的失败原因。

内环 · 毫秒级 · 每源抖动缓冲

// 每个源的目标水位。jitter 用 RFC 3550 的到达间隔抖动递推式估计
target_ms = clamp(2.0 * jitter_p95_ms + 10.0, 20.0, 150.0)

// 水位调整必须"慢"，否则音画偏移会呼吸
if (underrun)                 target_ms += 5.0;      // 一次 +5 ms
if (overrun && 持续 > 2s)     target_ms -= 2.0;      // 一次 -2 ms

注意"加得快、减得慢"。加慢了会持续断音（用户立刻察觉），减快了会让延迟来回跳（音画同步开始漂）。

外环 · 秒级 · offset 估计 + 重采样比率

// 源端每 500 ms 发一次 ping，Hub 立即回 pong
// t1 = 源发送时刻，t2 = Hub 收到，t3 = Hub 回复，t4 = 源收到（各自单调时钟）
rtt   = (t4 - t1) - (t3 - t2);
offset = ((t2 - t1) + (t3 - t4)) / 2;        // Hub 时钟 − 源时钟

if (rtt > 2 * min_rtt) return;              // 丢弃被排队/重传污染的样本
push(offset_window, offset);                 // 窗口 50
clock_offset = median(offset_window);        // 中位数抗抖动（Snapcast 同款）

有了 offset，源端每个包就能换算成 Hub 时间轴上的应播时刻：

deadline_hub_us = capture_ts_us + clock_offset + L_base_us;

然后把这个"应播时刻"和"实际播出时刻"的偏差喂给 PI 控制器，输出重采样比率（典型范围 ±0.2%）：

// 每 200 ms 调一次；慢比快重要
float pi_update(src_t* s, float meas_ms, float target_ms) {
    float err = meas_ms - target_ms;
    s->integ += err * KI * 0.2f;
    s->integ  = clampf(s->integ, -0.002f, 0.002f);
    return clampf(1.0f + KP * err + s->integ, 0.998f, 1.002f);
}

7.3 为什么不用 NTP / PTP

方案精度为什么不行 / 行
系统 NTP±10 ms精度不够，且系统时钟会被 NTP 校正"跳变"，音频时钟必须单调
PTP (IEEE 1588)±1 µs需要网卡/交换机硬件支持，家用 WiFi 路由器基本没有
自建 ping/pong + 中位数±0.1–1 ms选这个 局域网 RTT 稳定，中位数滤波足够；且完全可控

而且我们的精度需求本来就不高 —— 目标是"延迟锁在 60±5 ms"，不是"采样级对齐"。±1 ms 的时钟误差完全够用。

7.4 漂移：不处理一定会崩

手机晶振典型偏差 ±20–100 ppm。100 ppm × 1 小时 = 360 ms。不补偿的话，一小时会话里缓冲要么被撑爆（延迟涨到几百 ms），要么被抽干（持续断音）。

08播放端（Hub）

实时音频的规矩只有一条：回调里什么都别做。

8.1 线程模型

[UDP socket]  ──▶  每源 jitter buffer (SPSC 无锁环)  ──▶  [Decode+ASRC 线程]
                                                              │
                                                              ▼
[设备回调]  ◀──  输出环 (SPSC)  ◀──  [Mix 线程，每 5 ms 一个 block]

设备回调线程（WASAPI 的 realtime 线程 / AAudio 的 MMAP 回调）里只允许 memcpy：不能 new、不能 free、不能加锁、不能打日志、不能碰网络。 任何一次超过周期长度的阻塞都会变成可听见的爆音，而且这种 bug 在开发机上几乎复现不出来。

8.2 输出 API 选择

平台API可达设备周期取舍
WindowsWASAPI shared + IAudioClient32.67–10 ms
（取决于驱动是否 WaveRT）		能和别的 App 共存；老驱动只能到 10 ms
WASAPI exclusive2–10 ms更低更稳，但独占设备，Hub 本机的其他声音全静音
AndroidAAudio + LOW_LATENCY + EXCLUSIVE5–20 ms（MMAP 路径）Android 8.1+；缓冲设 2× burst；不加 LOW_LATENCY 会掉到 200 ms
macOSCoreAudio HAL2–10 ms—

参考实测（Google 官方 OboeTester 往返延迟）：全套低延迟配置 20 ms；只把 performance mode 关掉 → 205 ms；不用 MMAP 回调 → 62 ms。差距是数量级的，这些开关不是"优化"，是"能不能用"。

8.3 必须扣掉的"隐藏延迟"

你写进缓冲的时刻 ≠ 声音真正出来的时刻。设备侧还有 1–3 个周期的排队。不扣掉这部分，你以为的 60 ms 其实是 80 ms。

平台读取实际输出延迟的方法
WindowsIAudioClient::GetCurrentPadding() × 帧长 + 驱动报告的 IAudioClock 位置差
AndroidAAudioStream_getTimestamp() 返回 framePosition + time，可精确到硬件播放位置
macOSkAudioDevicePropertyLatency + kAudioStreamPropertyLatency + safety offset

这个值要作为已知常量从 L_base 中扣除，并在统计面板里显示"实测端到端延迟"，而不是"设计延迟"。

8.4 混音

  • float32 累加，每源独立增益（dB），末端软限幅（tanh 或 3 ms lookahead limiter）。多源直接相加会削顶
  • 响度归一化：对每源做短时 LUFS（BS.1770）测量，增益向 -23 LUFS 靠，时间常数 1–2 s。不要用 AGC，会泵
  • 主源优先：默认策略是"最近活跃的源为主，其余 duck 到 -12 dB"；同时提供手动混音台（推子 / 静音 / 独奏）
  • 静音检测：某源连续 500 ms 低于 -60 dBFS 就暂停解码，省 CPU 和带宽
自捕获反馈

如果 Hub 同时抓本机音频，会把自己播出来的远程音频再抓一遍 → 无限回声。Windows 上必须用 PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE 排除自身； Android 上 Hub 抓本机音频同样会抓到自己的输出，需要用 excludeUid() 排除自己。

09音画同步

这是整个项目最硬的一节，也是最需要提前对齐预期的一节。

9.1 感知阈值：多少算"对得上"

标准音频超前音频滞后语义
ITU-R BT.1359 可察觉+45 ms−125 ms超过这个范围，普通观众开始觉得不对
ITU-R BT.1359 可接受+90 ms−185 ms仍能看下去，但明显不同步
EBU R37（整链）+40 ms−60 ms广播级要求
ATSC IS-191+15 ms−45 ms最严格

符号约定很重要：正号 = 声音早于画面。人对"声音早了"比"声音晚了"敏感得多（45 vs 125 ms）。 所以工程上宁可让音频略微滞后，也不要让它超前 —— 这也意味着我们的延迟预算应该偏向"迟到一点"而不是"提前"。

9.3 三条策略，按场景选

S1 硬压 USB 网络共享 / 有线 + 有线耳机 + 10 ms 帧 + 20 ms 缓冲 55–70 ms，BT.1359 可察觉区下沿 失去无线便利性
S2 视频侧补偿 源端播放器把视频延迟 L_audio − L_video_local，让音画在"到达耳朵/眼睛"时对齐 可以做到真正严丝合缝 只能对自家播放器生效；抓第三方 App 时做不到
S3 场景降级 音乐 / 播客 / 游戏环境音不要求音画同步，只要求"延迟低且稳" 体验良好 视频场景不适用
必须提前对齐的预期

如果目标是"手机上看 B 站，声音从电脑耳机出来，口型完全对得上" —— 在不改造播放器的前提下，这件事做不到。 可达的是"能感知到轻微延迟但可接受"（60–100 ms），或者走 S2 用自家播放器。

9.4 校准工具（必做，不是可选）

没有测量就没有优化。三个层次的校准：

  • 自动测量：Hub 播一个 1 kHz 单周期脉冲，源端用麦克风录回来，互相关取峰值 → 得到含设备输出的真实端到端延迟。精度 ±1 ms
  • 半自动：屏幕上闪白块 + 同时出声，用户按"早了/晚了"微调（类似音游校准）
  • 关键指标：不只看均值，更要看标准差。均值 70 ms / σ=3 ms 是可接受的；均值 60 ms / σ=25 ms 是灾难

13.1 用 Unity 做可行吗？

你是 Unity 背景，这个问题值得认真回答：

  • 可以做的：混音（OnAudioFilterRead 拿 float 缓冲做求和）、用 AudioSettings.dspTime 做时钟、UI、多端打包
  • 做不到的：Unity 在 Windows 上走 FMOD → WASAPI shared，缓冲通常约 1024 采样（48 kHz 下 ≈21 ms）且不可调，也拿不到 IAudioClient3。 另外 Unity 主线程的 GC 和调度抖动会传导到音频回调
  • 结论：Unity 适合 P0 的原型（一天就能听到声音、验证混音手感），但会吃掉约 1/4 的延迟预算且抖动不可控。 目标定在 60–100 ms 时 勉强够用；要冲 40 ms 必须换 native
务实建议

用 Unity 做 Hub 的 UI + 混音台（它对延迟不敏感），把"采集 / 传输 / 抖动缓冲 / 输出"四件事放进一个 native 库（Rust 或 C++），Unity 通过 P/Invoke 调用。 这样既复用了你的熟练度，又不让 GC 进音频线程。不要试图用 Unity 的 AudioSource 走网络流 —— 那会把所有缓冲控制权交给 FMOD。

14关键代码骨架

三段最核心的伪代码，能直接翻译成 Rust/C。

14.1 抖动缓冲 + 混音循环

// 设备回调：唯一允许做的事就是 memcpy
void device_cb(float* out, int frames) {
    size_t got = spsc_read(&out_ring, out, frames);
    if (got < frames)
        memset(out + got, 0, (frames - got) * 2 * sizeof(float));
}

// 混音线程：每 5 ms 生产一个 block（240 frames @ 48k）
void mixer_tick(void) {
    float acc[BLOCK * 2] = {0};

    for (int s = 0; s < nsrc; ++s) {
        float tmp[BLOCK * 2];
        if (!jb_read(&src[s].jb, tmp, BLOCK)) {
            opus_plc(&src[s].dec, tmp, BLOCK);   // 用 PLC 补，绝不补静音
        }
        for (int i = 0; i < BLOCK * 2; ++i)
            acc[i] += tmp[i] * src[s].gain;
    }
    soft_limit(acc, BLOCK * 2);                  // tanh / lookahead limiter
    spsc_write(&out_ring, acc, BLOCK);
}

14.2 按 deadline 播出（而不是按到达顺序）

// Hub 时间轴上，这一帧应该在这个时刻被听到
int64_t deadline = pkt->capture_ts_us + src->clock_offset + L_base_us;

// 逆算它该在输出环的哪个位置（不需要排序，直接算出索引）
int64_t offset_frames = (deadline - now_hub_us) * 48000 / 1000000;
if (offset_frames < 0) {                 // 迟到：已经过了播出点
    stats->late_pkts++;
    if (-offset_frames > 48000 * 0.02)   // 迟到超过 20 ms 就丢弃
        return;
}
jb_write_at(&src->jb, pcm, nframes, offset_frames);

14.3 延迟上报（给 UI 和自动化测试用）

// 端到端延迟 = 采集时刻 → 真正出声时刻
latency_ms = (device_playout_us_now - (pkt->capture_ts_us + src->clock_offset)) / 1000.0;

// 上报均值与标准差；标准差比均值更能说明体验好坏
stats_push(latency_ms);
report(mean(lat_window), stddev(lat_window), jitter_p95, xrun_count);

实验怎么做能验证什么预计耗时

说明

文中延迟数字分为两类：设计推导值（采集/编码/缓冲等可计算的环节）与实测量级（引用他人测试或社区报告）。 两者都随设备、网络、系统版本大幅变化，落地时必须以 §09.4 的校准工具在你自己的硬件上重测。 特别是「AudioRelay ~50 ms」「Snapcast 30–200 ms」这类数字来自第三方测试，不是厂商承诺值。
