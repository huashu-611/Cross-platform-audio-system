# AudioHub 双端整体设计方案

> 版本：v2.0（重构）
> 适用：Windows 桌面端（Electron + C++ 音频核心）与 Android 端（原生 Java）
> 主题：**先建立连接，再分配角色**。连接前及连接过程中，两端都是对等设备，不预设源端/汇聚端；连接建立后才由用户（或默认规则）确定汇聚端。

---

## 1. 设计目标与原则

### 1.1 产品目标

把多台设备正在播放的声音，实时汇到**一台设备**的扬声器/耳机里，且：

- 不要求预先知道 IP（有自动发现），也允许手动指定（广播被拦的网络）
- 建立连接需要对方明确同意（可配置为自动接受）
- 谁当汇聚端由用户在**连接之后**决定，默认 PC
- 每台已连接设备的音量独立可调，实时生效
- 端到端延迟目标 < 150ms（同一 WiFi 下）

### 1.2 设计原则

| 原则 | 落地方式 |
|---|---|
| 连接与角色解耦 | 连接只管"能不能连上"，角色在连接之后分配 |
| 两端能力对称 | 都能采音、都能放音、都能发起/接受连接；协议与界面同源 |
| 广播只是便利功能 | 永远保留手动/单播通路，办公网拦广播也可用 |
| 状态机驱动 UI | 界面只是状态机的投影，不出现"界面显示已连接但底层没连" |
| 不做全量重绘 | 高频轮询只更新动态属性，避免点击/拖动被打断 |

## 2. 角色与术语

| 术语 | 含义 |
|---|---|
| **对等设备（Peer）** | 连接前与连接过程中的身份。两端在此阶段完全对等 |
| **汇聚端（Hub）** | 连接建立后承担"收流 + 混音 + 播放"职责的那一端，全网同时只有一台 |
| **音源（Source）** | 非汇聚端的设备。采集本机声音，经 UDP 送到汇聚端 |
| **会话（Session）** | 一组已确认连接构成的工作态，持续到全部断开 |

**关键约束**：

- 汇聚端是会话级属性，不是设备属性。设备随时可以换。
- 默认 PC 为汇聚端；手机之间互连时，由先建立连接的一端临时担任，可手动切换。
- 本机可以既是汇聚端又把自己的声音送进混音（回环）。

### 3.1 模块总览

```
│  ├─ 抖动缓冲（按绝对采样序号索引，非队列）                 │
│  ├─ 每路独立增益的混音（逐路乘增益后软限幅）               │

└──────────────────────────────────────────────────────────┘
```

### 3.1.1 音频样本的标度约定（跨端必须一致）

- **混音、增益、软限幅（0.85 阈值）、dBFS 统计全部在归一化 [-1, 1] 域里做。**
- int16 样本进混音前必须乘 `1/32768`，出播放设备前乘 `32767` 再取整。
  C++ 侧见 `src/hub_core.cpp` 的 `scratch[i] = src[i] * (1.0f / 32768.0f)`；
  Java 侧见 `ReceiverService.playLoop`。
- 这条约定踩过坑：`716c4b4` 重构 Java 接收端时丢了 `/32768`，混音一直停留在 int16 量级，
  软限幅把每个 `|x| > 0.85` 的样本压成 ±1 → 输出是满幅方波，听感为持续的电流音/爆音
  （`3ba77d9`、`40491ec` 改的都是它的表面症状）。改动音频数据流时，先 grep
  `mix[`、`SoftLimit`、`levelSum`、`track.write` 这些消费点，确认域一致。

## 4. 页面结构

两端**信息架构完全一致**，只是渲染技术不同（SVG vs Canvas）。

### 4.1 连接界面（Connect）

用途：让两台设备建立一条连接。此阶段**没有"汇聚端"概念**。

```
┌──────────────────────────────────────┐
│ AudioHub  连接设备           [地址]  │
│ 多台设备的声音，汇到一处              │
├──────────────────────────────────────┤
│ 连接请求（有待确认时出现）            │
│  ┌ 警示条：某设备 请求把声音送到这里  │
│  │ [同意] [拒绝]                     │
├──────────────────────────────────────┤
│ 发现的设备                 [扫描]     │
│  [扫描结果提示行]                     │
│  ┌ 设备名  音源 / 汇聚               │
│  │ ip:port         [邀请] [连入]     │
│  └                                    │
├──────────────────────────────────────┤
│ 按 IP 直接邀请 / 手动添加             │
│  [输入框 ip:port]            [邀请]   │
└──────────────────────────────────────┘
```

### 4.2 控制界面（Control）

用途：看会话、调音量、改汇聚端。

```
┌──────────────────────────────────────┐
│ AudioHub  控制台                     │
├──────────────────────────────────────┤
│              网络图                   │
│         ⬤ 汇聚端（大球 + 光晕）       │
│        ╱   │    ╲                    │
│      ⬤    ⬤     ⬤   （各设备小球）   │
│  —— 点球可调该设备音量 ——             │
├──────────────────────────────────────┤
│ 音量面板（点球后展开）                │
│  设备名      [滑杆 0–150%] 100% [静音]│
├──────────────────────────────────────┤
│ 汇聚端：当前设备名      [切换]        │
├──────────────────────────────────────┤
│ 会话：设备 N 台 / 总线 / 码率 / 欠载  │
│ [断开所有连接，回到连接界面]          │
└──────────────────────────────────────┘
```

### 4.3 状态机（两屏切换的唯一依据）

```
                ┌──────────────────────────┐
                │        IDLE（无会话）     │
                │     显示连接界面          │
                └───────────┬──────────────┘
                            │ 第一条连接被确认
                            ▼
                ┌──────────────────────────┐
                │      SESSION（会话中）    │
                │     显示控制界面          │
                └───────────┬──────────────┘
                            │ 全部连接断开 / 用户主动离开
                            ▼
                         IDLE
```

**不允许**出现"没有会话却停留在控制界面"的状态；连接丢失后自动回到连接界面。

## 5. 数据模型

### 5.1 设备（Peer）

```jsonc
{
  "name": "客厅PC",          // 显示名，UTF-8
  "ip": "10.135.129.59",    // 已剔除虚拟/TUN 网卡后的候选地址（可能多个）
  "audioPort": 47000,
  "httpPort": 0,
  "canReceive": true,        // 能力声明，两端恒为 true（对称）
  "canSend": true,
  "lastSeenMs": 1710000000
}
```

### 5.2 连接（Connection / Source）

```jsonc
{
  "id": 1,                    // streamId，连接期由发起方指定
  "peerName": "书房PC",
  "confirmed": true,          // 未确认 = 不收流不发声
  "gain": 1.0,                // 0–4.0，UI 映射 0–150%
  "muted": false,
  "level": -12.4,             // dBFS，RMS 平滑
  "occupancy": 62,            // 抖动缓冲水位（ms）
  "packets": 12800,
  "underrun": 0,
  "overflow": 0
}
```

### 5.3 会话快照（State，每 200ms 推给 UI）

```jsonc
{
  "ip": "10.135.129.59:47000",
  "busLevel": -9.2,
  "master": 1.0,
  "latency": 60,
  "kbps": 373.5,
  "autoAccept": false,
  "renderUnderruns": 0,
  "malformed": 0,
  "sources": [ Connection... ],
  "peers":   [ Peer... ],
  "pending": [ { "streamId": 1, "name": "...", "ip": "..." } ],
  "error": null
}
```

### 5.4 角色状态（RoleState）

```
hubSelf : bool        // 本机当前是否是汇聚端
hubName : string      // 汇聚端显示名（本机或对端名）
hubAddr : string      // 汇聚端地址（本机为空）
```

角色状态只在**会话建立后**才有意义，连接界面不展示也不读取。

## 6. 通信机制

### 6.1 端口分配（UDP）

| 端口 | 用途 |
|---|---|
| 47300 | 发现信标与 WHO 探测（广播 + 单播） |
| 音频口（默认 47000） | 音频数据帧 |
| 音频口 + 1 | PING / PONG（时钟同步与 RTT） |
| 音频口 + 2 | 连接握手（CONN-REQ/ACK/NAK/BYE/INVITE） |

### 6.2 发现协议

```
信标：AUDIOHUB|1|<role>|<audio_port>|<http_port>|<候选IP列表>|<显示名>\n
探测：AUDIOHUB|1|WHO\n
```

要点：

- **每网卡各绑一个临时 socket 发送**：保证从正确网卡出去（Clash/VMware 默认网卡不可信）
- 每个网卡同时发"限定广播 255.255.255.255"和"本网段定向广播"，覆盖两端掩码不一致
- 收到 WHO 立刻单播回信标，不必等下一个 1 秒周期
- **单播探测** `probeTo(ip)`：广播被拦的网络里唯一的自动发现手段
- 候选 IP 已剔除 198.18/15（Clash）、100.64/10、169.254、虚拟网卡

### 6.3 握手协议（只负责"连接"，不含角色）

```
发起方 → 接收方：CONN-REQ|<发起方名>|<streamId>
接收方 → 发起方：CONN-ACK|<接收方名>|<streamId>   （同意）
                 CONN-NAK|<原因>|<streamId>        （拒绝）
任一方           ：CONN-BYE|<streamId>             （断开）

汇聚端 → 对端：CONN-INVITE|<汇聚端名>|<ip:音频口>   （邀请，反向建立）
```

### 6.3.1 角色控制帧（ROLE）

连接建立之后，一端可以远程指挥另一端切换角色，避免两端各点一次：

```
ROLE|hub                     → 你来当汇聚端（开始接收）
ROLE|source|<ip>:<port>      → 你把声音送到 ip:port（当音源）
```

- 走握手口（音频口 +2），与 CONN-* 同一通道
- 接收方执行后回一个 Toast 说明发生了什么
- **安全边界**：局域网明文、无鉴权。同网段任何设备都能发。
  作为内网工具可接受；若要跨不可信网络，需加配对密钥（token）
  并在 ROLE 帧里带上

桌面端由 `POST /api/role {ip, audioPort, hub, hubIp, hubPort}` 触发。

> **v2.1 起改为图谱驱动**：界面上的汇聚端切换走**共享网络图谱协议**
> （[GRAPH-PROTOCOL.md](GRAPH-PROTOCOL.md)）：每端维护同一张设备图，点图上任意节点
> 即本地切换并把新图谱广播给全网，各端 1~2 秒内收敛，不再需要给每台设备单独发 ROLE。
> ROLE 帧与 `/api/role` 保留为兼容接口，新界面不再调用。

关键实现约束：

- **未确认的流完全不取水**：否则抖动缓冲被抽干，确认后回不来
- 确认时 Reset 抖动缓冲与 ASRC
- `accepted_ids` 记住已确认 streamId：握手模式下发起方收到 ACK 才开始发包，Accept 时流往往还不存在
- BYE 后流被移除，若对端继续发包会以未确认状态重新出现

### 6.4 音频帧

```
[1B 版本/标记][1B 通道][2B streamId][4B 序号][4B 采样位置][2B 保留] + PCM16 小端
48000 Hz / 双声道 / 每包 240 帧 = 5ms
```

## 7. 核心业务流程

### 7.1 流程 A：设备发现

```
A 打开 App → 每网卡广播信标 + 主动 WHO 探测
B 收到 WHO → 立刻单播回信标
A 收到信标 → 校验格式 → 选择同网段 IP → 加入设备列表
UI：列表按"签名"更新，扫描按钮给出即时结果提示
异常：广播被拦 → 用户手动填 IP / 单播探测上次地址
```

### 7.2 流程 B：建立连接（此阶段无角色）

```
发起方                       接收方
  │  点击"连入"或"邀请"        │
  ├──── CONN-REQ ─────────────▶│
  │                            │ 进入待确认列表，UI 弹警示条
  │                     [同意] / [拒绝]
  │◀──── CONN-ACK ─────────────┤
  │                            │ accepted_ids 记录 streamId
双方进入 SESSION → 界面切到控制界面
```

### 7.3 流程 C：分配角色（连接之后）

```
进入 SESSION
  └─ 默认规则：若对端是 PC，则 PC 为汇聚端；否则先建立连接的一端临时担任
  └─ 用户在控制界面点「切换」→ 选择会话中的任一端
       ├─ 新汇聚端：启动收流/混音/播放
       └─ 其余各端：重定向音频流到新汇聚端
  └─ 界面上的"大球"随角色迁移，大小与光晕同步变化
```

### 7.4 流程 D：实时音量

```
点球 → 选中高亮 + 连线加粗 → 音量面板展开
拖滑杆 → 本地立即生效（不动 DOM），同时下发增益
  桌面：POST /api/source {id, gain}
  手机：ReceiverService.setStreamGain(id, gain)
混音线程每 5ms 按最新增益混音 → 听感实时变化
松手 → 恢复由状态驱动的显示
```

### 7.5 流程 E：断开与异常

```
对端超时 5s 无包 → 流被移除 → 该球消失
全部断开 → 回连接界面
音频核心不可达 → 顶部警示条（不遮挡操作）
扫描无结果 → 空态文案 + 本机 IP + 同网段提示 + 手动添加入口
```

## 8. 异常与边界处理

| 场景 | 处理 |
|---|---|
| 加载中 | 扫描按钮进入"扫描中…"并禁用，结果返回后恢复 |
| 空设备 | 显示"正在扫描/暂未发现" + 本机 IP + 手动添加入口 |
| 音频核心未就绪 | 顶部 banner 提示原因，按钮降级而不是白屏 |
| 未确认连接 | 警示条置顶；不收流、不发声 |
| 拒绝连接 | 发起方收到 NAK，提示"对方拒绝" |
| 对端掉线 | 5 秒无包移除流；节点消失；全部断开则回连接界面 |
| 端口被占 | 明确告警"发现不可用/音频口被占"，并给手动方案 |
| 角色切换 | 先停旧汇聚端接收，再启新汇聚端；大球大小与光晕同步变化 |
| 重复点击 | 扫描/邀请按钮在途禁用；音量拖动期间不被状态回写 |
| 屏幕尺寸 | 网络图按视图尺寸等比布局；窄屏节点改纵向排列 |
| 进程被强杀 | 前台服务保活；WakeLock + WifiLock 防止锁屏断流 |
| 角色切换瞬间 | `hubLabel` 等展示字段必须有兜底：此时对端地址可能还是 null，一路传到 `Canvas.drawText(null)` 会直接 NPE 闪退 |
| 崩溃排查 | 全局 `UncaughtExceptionHandler` 写 `files/crash.txt`；下次启动弹窗展示并支持一键复制 |

## 9. 视觉与交互规范

| 项 | 规范 |
|---|---|
| 主色 | `#3B82F6`（蓝），与图标一致 |

## 10. 验收清单

- [ ] 连接前不出现"汇聚端"选择；连接后才可设定
- [ ] 默认 PC 为汇聚端；切换后大球随之迁移且大小变化
- [ ] 两端都能发起/接受连接，握手需要确认
- [ ] 点球可调该设备音量，实时生效，拖动不被打断
- [ ] 双端都显示同一张网络图（角色不同则大球不同）
- [ ] 邀请/扫描按钮可稳定点击（无高频重绘打断）
- [ ] 广播被拦时可手动添加 / 单播探测连接
- [ ] 断连后自动回连接界面；核心不可达有明确提示
- [ ] 空态、加载态、异常态均有对应文案与入口
- [ ] 单元测试全过；两端产物可独立安装运行
