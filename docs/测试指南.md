# 单机测试指南

目标：**只用一台 Windows PC**，验证「多路音频汇聚到同一台设备的扬声器/耳机」这条链路是否成立。

---

## 0. 准备

```bash
./build.sh          # 产物在 build/
```

- Windows 10 2004 或更新（用到 WASAPI loopback）
- **戴有线耳机**。蓝牙耳机一次性加 150~250 ms，会把所有延迟指标污染掉，测什么都看不出
- 三个终端窗口（PowerShell / cmd / Git Bash 都行）

> 第一次跑会被防火墙拦一下，允许即可。数据口 47000，控制口 47001。

---

## 1. 场景 A：多源混音（推荐先跑这个）

不依赖声卡、不依赖任何播放器，纯信号源。**这是最快能判断"东西到底通没通"的办法。**

**终端 1 —— 汇聚端（出声的那台）**

```bash
build/audiohub-hub.exe --port 47000 --latency 60
```

**终端 2 —— 源 1，440 Hz**

```bash
build/audiohub-source.exe --hub 127.0.0.1:47000 --tone 440 --stream-id 1
```

**终端 3 —— 源 2，660 Hz**

```bash
build/audiohub-source.exe --hub 127.0.0.1:47000 --tone 660 --stream-id 2
```

### 应该看到什么

终端 1：

```
[6 s] 收 405 pkt/s (3162 kbps) | 混音总线   -6.0 dBFS | 渲染欠载 6 | 坏包 0 | 源 2 路
   stream 1   水位   51 ms (目标 60) | 比率 1.00004 | 电平   -9.0 dBFS | 迟到 0 溢出 0
   stream 2   水位   51 ms (目标 60) | 比率 1.00017 | 电平   -9.0 dBFS | 迟到 0 溢出 0
```

耳朵里应该是 **440 Hz 和 660 Hz 同时响**（纯五度，听起来协和）。

### 怎么判断对错（有硬指标，不用靠耳朵）

| 指标 | 理论值 | 实测 | 含义 |
|---|---|---|---|
| 单路电平 | −9.03 dBFS | −9.0 | 幅度 0.5 的正弦，RMS = 0.5/√2 |
| 总线电平 | −6.02 dBFS | −6.0 | 两路不相关信号功率相加，**恰好 +3.01 dB** |
| 收包速率 | 两路各 200 pkt/s | 405 | 5 ms 一包 |

**总线比单路高 3 dB 就是混音正确**。如果只高 0 dB，说明有一路被覆盖了；
高 6 dB 说明同一路被混了两遍。

## 2. 场景 B：抖动鲁棒性

给其中一路注入零均值随机抖动，模拟 WiFi：

```bash
build/audiohub-source.exe --hub 127.0.0.1:47000 --tone 660 --stream-id 2 --jitter 15
```

预期：

- 该路「水位」会略微抬升（抖动缓冲要吃下 ±15 ms 的到达抖动）
- 出现少量「欠载」是正常的，但**不应该持续增长**
- 「溢出」应当保持 0
- 声音不应该断，也不应该出现规律的咔嗒

把 `--jitter` 调到 40 再试一次：如果开始持续欠载，说明目标延迟 `--latency` 定得太低，
把 hub 改成 `--latency 120` 再跑。

## 3. 场景 C：真实音频

> **单机上不要直接这么跑。** source 抓的是「系统混音」，其中包含 hub 自己放出来的声音，
> 于是形成 环回 → 采集 → 再播放 的反馈回路，几十毫秒后就会啸叫/失控。

真实音频要等**第二台设备**（手机或另一台 PC）当源端：

- 手机跑 source，PC 跑 hub —— 两条链路物理隔离，不存在自捕获
- 单机的替代方案见场景 A（信号源），它验证的是同一套传输/缓冲/混音逻辑

## 4. 常见问题

**没声音**

1. 先看 hub 有没有打印 `[+] 新流接入: id=N`。没有 = 包没到，检查 IP 和防火墙
2. 有流但电平 −120 dBFS = 收到的是静音（可能是源端采集失败）
3. 电平正常但听不到 = hub 输出设备不对，或系统音量被静音

**端口被占用**

```bash
netstat -ano | findstr 47000
```

换一个 `--port 47100` 即可（控制口会自动用 47101）。

**水位一直在涨，最后溢出**

说明源端发得比 hub 消费得快，通常是源端进程被系统降频（笔记本省电模式）。
把电源计划改成「高性能」。

**蓝牙耳机**

不要用。A2DP 的缓冲在系统音频栈之外，程序无法感知也无法补偿。
听感上会明显"音画不同步"，而且所有延迟数字都会失真。

## 5. 一次跑完（脚本）

Git Bash 下可以直接跑完场景 A 并自动判定：

```bash
cd build
./audiohub-source.exe --hub 127.0.0.1:47400 --tone 440 --stream-id 1 >/dev/null 2>&1 &
./audiohub-source.exe --hub 127.0.0.1:47400 --tone 660 --stream-id 2 >/dev/null 2>&1 &
sleep 1
timeout 8 ./audiohub-hub.exe --port 47400 --latency 60 | grep -E "收 |stream"
taskkill //F //IM audiohub-source.exe >/dev/null 2>&1
```
